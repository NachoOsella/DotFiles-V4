# Pi Durable assumptions

Target: published `@earendil-works/pi-durable@1.0.0`, experimental. Published source maps include TypeScript source. Paths below are relative to that package's source. Official examples 22, 23 and 24 were compared with published declarations. Examples are not guarantees beyond the checked source. The installed coding-agent version is 1.0.0.

## Verification and limits

The test suite exercises native request-ID deduplication, same-answer reporting, idle and busy passive writes, both input queue modes, background abort through terminal anchors, wait cancellation, the reporter-before-initialization race, native prompt-section removal on a full fork, local fork usage, compaction, nested configuration reopen, and four SQLite SIGKILL boundaries. The changed-config replay test verifies the original spawn tool response, not only the surviving child.

Independent installed-API probes confirmed that request IDs deduplicate even if a repeated draft changes its payload, idle writes do not generate, forks inherit configuration, and fork usage starts empty. Independent extension probes drove real tools with provider capacity one and checked identity, overrides, inherited instructions/capabilities, reporting, passive messages and follow-up. The detailed reproducible boundary tests remain in `../test`.

`TaskRuntime.entry` reads within the invocation's bound conversation. Reporters instead use global `tx.entry(AssistantEntry, answerId)` to read a child's answer in a commit. Missing or non-assistant answer entries and broken non-root parent registry links fault explicitly rather than silently losing a report.

SQLite process-death tests do not establish power-loss durability. Native usage records committed spend, not an external provider billing ledger. A resumed request can execute again after a crash even though its logical input and report stay deduplicated.

No MCP extension is installed by the supplied host. Arbitrary foreign tool provenance is not represented by the absent exposure/namespace contracts; a caller-supplied registry must control selected extensions itself.

A package upgrade must rerun the suites and recheck this table before enabling the extension. Stable CLI integration and separately authorized cutover remain required.
